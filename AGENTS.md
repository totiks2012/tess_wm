## ЖЁСТКИЕ ПРАВИЛА (НЕ НАРУШАТЬ)

* **СМОК-ТЕСТЫ/СТАБЫ НИКОГДА НЕ ЗАМЕНЯЮТ РЕАЛЬНЫЕ БИНАРИ — ЗАПРЕЩЕНО.** Стабы и моки внешних команд (для виртуальных тестов, фейковых PATH/HOME и т.п.) создаются ТОЛЬКО во временных изолированных каталогах
 (`/tmp/opencode/*`) и передаются скрипту исключительно через подмену переменной окружения `PATH` (или `HOME`). 
Категорически запрещено записывать, перезаписывать, трогать или «исправлять» файлы в `/usr/bin`, `/bin`, `/usr/local/bin`, `/sbin` и прочих системных каталогах: они не являются песком, 
из них нельзя создавать стабы, и никакой «стаб поверх настоящего бинаря» недопустим — это ломает систему (после удаления тестового каталога бинарь остаётся битым скриптом-заглушкой). 
Перед тестом — убедиться, что подменяемое имя (`command -v`) находится только внутри тестового каталога. Если стабы всё же оказались в системе — немедленно восстановить бинари (`apt reinstall <пакеты>`), 
это критично. См. реальный инцидент ниже.
* **СТАБЫ СОЗДАВАТЬ ТОЛЬКО ЧЕРЕЗ ГОТОВЫЙ ХЕЛПЕР-ПЕСОЧНИЦУ:** руководиться правилом «дисциплиной это чинится» нельзя — дисциплина снижает частоту, а не даёт гарантию. 
Для любого смок-теста использовать готовый хелпер `vtest.sh` (лежит в `~/.local/bin/me/me_lib/vtest.sh`, автономен, можно скопировать в проект): 
песочница создаётся только под `/tmp/opencode/<имя>/`, стабы пишутся только внутрь неё (guard-проверка пути с отказом при попытке выйти за пределы), 
запуск теста — только через `vtest run <песок> -- <команда>`, `vtest verify`/`vtest audit` подтверждают, что команда резолвится только в песочнице и в системе не осталось следов. Руками стабы не писать.

## Парадигмы и принципы
* **KISS & Suckless:** Код должен быть максимально простым, модульным, прозрачным и без скрытых зависимостей.
* **Предсказуемость:** Выдача кода происходит строго по требованию. Изменения вносятся только в целевые компоненты.
* **Stream-ready:** Структурирование проекта должно быть явным и удобным для конвейерной обработки (POSIX-style).
* **Zero assumptions:** Если задача описана не полностью — не додумывай. Запроси недостающее.
* **Риск-анализ:** Прежде чем менять существующий код или архитектуру — агент ОБЯЗАН предупредить пользователя о Вероятных рисках: что сломается, что перестанет работать, какие методы потеряют функциональность. Изменения вносятся только после явного подтверждения.
* **Регрессия:** Прежде чем вводить новый метод, менять существующий или переписывать компонент — агент ОБЯЗАН проверить, что изменения не ломают другие методы и компоненты системы. Проверка: `bash -n` для всех скриптов, тестовый запуск затрагиваемых методов.
* **Не трогать бэкапы:** Агенту СТРОГО ЗАПРЕЩЕНО изменять, удалять или создавать файлы в каталогах с именами `bac`, `bacup`, `BAC`, `BACUP` и их аналогами. Это резервные копии — не рефакторить, не править, не чистить.

## ЧАСТЬ 1. ИДЕЯ (как я её понял)

```
## Идея: wm-tview — оконный менеджер модальных окон поверх tview

### Что это

Не фреймворк виджетов (это делает tview).
Не тайловый WM в терминале (это делают tmux/zellij).
А слой поверх tview, который добавляет то, чего в tview нет:
много модальных окон, сосуществующих во времени, с фокусом и переключением.

### Ключевая механика

1. Основное приложение на tview (Root + Flex/Grid + виджеты).
2. Поверх него — оконный менеджер, который умеет:
   - Создавать окна динамически (API)
   - Держать их открытыми одновременно
   - Переключать фокус между ними (хоткеи)
   - Рендерить активное окно, буферизовать неактивные
   - Закрывать окна по команде
3. Содержимое окна — ЛИБО tview.Primitive (виджет), ЛИБО живой субпроцесс в pty
   (shell, bash-скрипт, любая интерактивная программа).
4. Субпроцесс в окне — не «одноразовый вызов» (как exec.Command),
   а долгоживущая сессия, с которой пользователь взаимодействует.

### Чем отличается от существующего

- От tmux/zellij: внутри одного Go-процесса, окна — объекты, а не процессы;
  субпроцессы живут внутри окон, а не вместо них.
- От tview.Pages: Pages переключают содержимое одного Root;
  здесь — независимые окна со своим состоянием, z-order, фокусом.
- От tview демо embed: там embedding в TextView для одной программы;
  здесь — полноценная оконная система с менеджером.
- От lazygit/lazydocker/k9s: там панели жёстко закодированы;
  здесь — окна создаются динамически через API.

### Зачем это нужно

Среда, в которой:
- Редактор + shell + git + diff — в разных окнах, переключение хоткеем.
- Мониторинг: htop + tail логов + docker ps + свой скрипт — рядом.
- Твоя me-среда: модальные методы как полноценные окна,
  а не одноразовые fzf-меню.
- Отладка: код + вывод тестов + shell для ручных команд.

### Примеры применения (конкретно)

1. Открыл окно с vim → открыл окно с shell → Ctrl-N между ними.
2. Открыл окно с git status → открыл окно с diff → переключаешься.
3. Из me запустил долгий скрипт в окне → переключился на другое дело →
   вернулся, скрипт работает, лог на месте.

### Базовая архитектура (для ориентира)

Слой 1 — Оконный менеджер (наше):
  - Список окон []*Window
  - Активное окно *Window
  - Z-order, фокус, хоткеи переключения
  - События: created/activated/deactivated/closed

Слой 2 — Окно (Window):
  - Содержимое: tview.Primitive ИЛИ pty.Session
  - Заголовок, границы, регион рендера
  - Метод Draw(screen tcell.Screen) — рендер в свой регион

Слой 3 — Адаптеры содержимого:
  - WidgetAdapter — оборачивает tview.Primitive
  - PTYAdapter — оборачивает pty-сессию (рендер вывода, передача ввода)
  - ScriptAdapter — запускает bash-скрипт в pty, отдаёт результат

Слой 4 — Пользователь API:
  - wm.NewWindow(...) / wm.NewShellWindow(...) / wm.NewScriptWindow(...)
  - wm.Bind("C-n", wm.NextWindow)
  - wm.OnWindowClose(func(w *Window) {...})

### Ключевые сложности (для агента — знать, но не решать в шаге 1)

1. Рендер нескольких pty параллельно: буферизация вывода, событийный рендер,
   не терять вывод неактивных окон.
2. Ресайз pty при ресайзе окна: SIGWINCH + перерендер.
3. Конфликт хоткеев: Ctrl-N хочет и WM, и vim в активном окне.
   Решение (префиксные хоткеи, модальность, явные Alt-хоткеи) — принять позже.
4. Передача ввода в неактивные окна, требующие ответа (yes/no, пароль):
   UX-вопрос, решать позже.

### Философия проекта

- Использовать tview, НЕ писать свой фреймворк виджетов.
- Начинать с малого: одно окно → два окна → API → интеграция с me.
- НЕ писать «WM вообще». НЕ писать «для других».
  Сначала для себя. Один сценарий. Хорошо.
- Если через месяц не используется ежедневно — остановиться.

```
## SEED: Шаг 1 — один shell в модальном окне поверх tview

### Цель шага

Доказать, что связка tview + tcell + pty работает:
открыть модальное окно с живым bash-процессом внутри,
получить от него вывод, отправить ввод, корректно закрыть.

ЭТО НЕ ФРЕЙМВОРК. ЭТО ПРОТОТИП ОДНОГО ОКНА.
Не добавляй оконный менеджер, API, переключение фокуса.
Только одна программа с одним окном.

### Что должно быть

Одна Go-программа (prototype). При запуске:
1. Показывает базовый tview-UI: например, TextView с текстом
   «Основное приложение. F1 — открыть shell».
2. По F1 — поверх открывается модальное окно с bash-процессом внутри.
3. В окне bash: можно печатать команды, видеть вывод, курсор работает.
4. По Ctrl-D в bash (или по F1 повторно) — окно закрывается,
   возврат к основному UI.
5. Основной UI остаётся на экране под окном.

### Обязательные требования

R1. tview для UI, tcell как движок (tview его использует).
R2. creack/pty для создания pty и запуска bash.
R3. Окно занимает, например, центральные 80% экрана, с рамкой и заголовком «shell».
R4. Вывод bash рендерится в окне корректно:
    - ANSI-цвета работают (ls --color, git status)
    - Курсор виден и позиционируется
    - Перенос строк работает
R5. Ввод пользователя идёт в bash: буквы, Enter, Ctrl-C, стрелки (история).
R6. Ресайз терминала: при изменении размера основного окна
    pty получает SIGWINCH с новыми размерами, bash перерисовывается.
R7. При закрытии окна bash-процесс корректно завершается (не остаётся зомби).
R8. При выходе из программы (Ctrl-C в основном приложении) — bash тоже убит.

### Что НЕ делать в этом шаге

- НЕ делать второе окно, переключение фокуса, список окон.
- НЕ делать API для создания окон (wm.NewWindow и т.п.).
- НЕ делать WidgetAdapter/ScriptAdapter (только PTYAdapter, неявно).
- НЕ делать сохранение состояния между запусками.
- НЕ интегрировать с me — пока отдельный прототип.
- НЕ использовать bubbletea (только tview).
- НЕ писать свой терминальный эмулятор — использовать готовое.

### Что использовать

Обязательно изучить и, если подходит, взять за основу:
- github.com/rivo/tview — UI
- github.com/gdamore/tcell/v2 — движок
- github.com/creack/pty — pty

ОБЯЗАТЕЛЬНО посмотреть пример tview/demos/embed —
там embedding внешней программы в TextView через pty.
Это ближайший референс. Возможно, большую часть можно
адаптировать оттуда, а не писать с нуля.

### Структура проекта (предложение, не догма)

prototype/
  main.go       — точка входа, tview-приложение, F1-хоткей
  shell_window.go — окно с pty-сессией, рендер, ввод, ресайз
  go.mod        — модуль + зависимости

### Критерии приёмки

A1. go build ./... — успешно.
A2. go vet ./... — без замечаний.
A3. При запуске — виден основной tview-UI.
A4. По F1 — поверх открывается окно с живым bash.
A5. В bash работают: ls --color, git status (если есть репо), Ctrl-C,
    стрелки вверх/вниз (история), Tab (автодополнение).
A6. Ctrl-D в bash — окно закрывается, возврат к основному UI.
A7. Повторное F1 — снова открывает bash (новый процесс).
A8. Ресайз окна терминала — bash в окне корректно перерисовывается.
A9. После выхода из программы — нет зомби-процессов bash
    (проверить через ps aux | grep bash).
A10. Прототип работает в обычном терминале (xterm/alacritty/kitty).

### Риски (агент обязан предупредить пользователя)

R-1. tview не имеет встроенной поддержки «модальных окон поверх» —
     возможно, придётся использовать tview.Pages и Flex,
     либо рендерить окно через tcell поверх tview.
     ЭТО ГЛАВНЫЙ ТЕХНИЧЕСКИЙ РИСК ШАГА.

R-2. Синхронизация рендера tview и вывода pty —
     возможны мерцания, если рисовать из двух источников.
     Возможно, потребуется единый цикл рендера.

R-3. Курсор: tcell управляет курсором сам, pty тоже присылает
     escape-последовательности позиционирования курсора.
     Возможен конфликт. Решение — принять по факту.

R-4. Некоторые escape-последовательности (alt-screen, mouse)
     могут не работать в embedded-режиме.
     Это ограничение принять как известное.

R-5. Если pty не даёт корректный вывод при первом подключении —
     проверить TERM-переменную (должна быть типа xterm-256color).
